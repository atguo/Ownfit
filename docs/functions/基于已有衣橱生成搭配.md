# 基于已有衣橱生成搭配

版本：v0.5｜设计草案｜2026年10月26日  
所属项目：[项目计划书](../项目计划书.md)

## 1. 功能目标与问题

解决“今天想穿这件衣服，其他怎么配”。输出真实衣橱中可穿的组合，避免只生成无法落地的搭配图片。

## 2. 范围与边界

第一版优先锁定一件已有单品，再选择上衣、下装、鞋履和配饰等。颜色、风格与参考图元素作为后续可扩展起点。

只使用已有衣服的模式不得添加虚构单品。此功能负责组合与理由；本人图像生成、天气适配、商品补购由对应功能负责。

## 3. 使用场景与流程

锁定单品 → 选择场景、时间与限制 → 获取个人偏好和环境条件 → 结构化资料筛选 → 候选图片复核 → 形成少量有区别的方案 → 用户选择 → 按需进入本人预览。

例：用户锁定灰色阔腿裤，要求明天上班穿、主要在办公室、晚上步行回家。系统根据环境约束与衣橱生成方案，说明所选单品和穿法；需要预览时只传当前套装。

## 4. 关键设计与理由

采用“文字与结构化资料初筛 → 图片复核 → 具体方案”的流程，避免每次向模型传整个衣橱，也避免仅用文字丢失颜色、纹理与版型关系。

| 环节 | 规则与理由 |
| --- | --- |
| 硬条件过滤 | 排除清洗中等确定不可用单品，以及违反明确要求的组合 |
| 软条件排序 | 比较配色、风格、偏好与环境适配，不把模糊标签当成绝对排除条件 |
| 整套判断 | 按穿法和叠穿评估，例如短袖冬季可作内搭 |
| 图片复核 | 读取缩小范围后的图片，确认文字资料没有表达清楚的外观关系 |
| 方案输出 | 明确单品引用、穿法、推荐理由与资料缺口，不只给一张图 |

候选数量、排序权重和图片复核方法待实验确定。该方案是设计方向，不代表已验证模型成本或效果。

### 4.1 局部修改与撤销

已确认，纳入第一版：用户可锁定满意单品，只替换指定的一件；也可保留选中组合，要求更正式、更休闲或更保暖。系统在保留锁定条件下调整未锁定项或穿法，不能暗中解锁。

条件冲突或所有单品均已锁定且无法满足要求时，说明原因，让用户选择解锁某件或保留原方案。替换不喜欢、今天不能穿、实际不舒服等原因可选填，其采集与归因规则见[反馈文档](穿着反馈与搭配收藏.md)。

每次修改形成方案版本，记录父版本、锁定项、变更项和当次要求。支持撤销到上一版本；已有版本的预览保持对应，未生成新图时不能拿旧图代表新方案。撤销恢复方案内容，执行或重穿时仍检查当前可用状态。

### 4.2 输出有实际差异的方案

少量方案按用户需求形成可理解的区别，如日常稳妥、稍正式、尝试新组合。标签说明实际差别，不为了数量强凑无区别的结果；只换一双鞋时应诚实标为局部变体。

首次任务不等待完整衣橱，遵循衣橱文档的任务式引导。未录入不等于未拥有；资料充足程度只约束用途，不替代适合度排序。长期偏好与当前要求按个人资料文档区分。

## 5. 数据与状态

输入：锁定元素、衣橱档案及可用状态、个人偏好、时间地点与场景、用户限制。

搭配请求保存以上上下文；方案保存单品 ID、档案版本、穿法、理由与缺口。后台初筛不触发逐件补全，所需资料由衣橱用途检查返回。

推荐任务与预览任务分别记录状态。推荐成功只代表形成组合，不代表图像已生成；预览失败不能清空已选搭配。

### 5.1 稳定业务契约与模型适配

页面和编辑状态消费版本化的业务方案，不直接依赖模型原始 JSON。契约包含请求限制、单品引用、方案/父版本、穿法粒度、原因与缺口、可选字段缺省及修改撤销规则。推荐原因未提供时按未知或缺省显示，不为满足字段要求制造理由。

测试方案和真实模型适配结果共用契约校验，覆盖部分缺项、不可执行穿法、全锁定冲突、过期版本和失败。客户端业务适配层负责模型输出到业务结构的转换；不能适配时明确失败或限制。

契约在 M3 实现前形成草案、验收时冻结 v1；真实能力在 M5 接入前验证适配。冻结不是禁止演进，必要变更需版本、影响评估和回归；时点与交付条件见 [开发计划](../开发计划.md) 第 6.3 节。

## 6. 异常与替代路径

没有合适衣服时明确缺口，允许换候选、放宽非固定条件或进入补购，不能偷偷替换用户锁定的单品。未知属性不等于确定不匹配，也不能被视为已满足关键限制。

非锁定单品缺关键证据时优先给替代候选；需用户补充时遵循衣橱统一频率规则。候选图片不可用或生成失败时保留请求与已形成方案，允许重试。

## 7. 功能依赖

[衣橱](衣橱资料入库与渐进完善.md)负责属性提取、来源与补充规则；[个人资料](个人资料管理.md)提供偏好；[天气](天气与场景适配.md)提供环境约束；[AI预览](AI上身预览.md)处理已选组合；[反馈收藏](穿着反馈与搭配收藏.md)保存方案及穿着评价；[商品匹配](灵感搭配与商品匹配.md)处理衣橱缺口。

## 8. 验收条件与待确认事项

新增验收：只换鞋时其他锁定单品不变；修改失败保留原方案；撤销恢复上个版本及对应预览引用；临时正式要求不改长期偏好；冲突需显式处理；方案区别可说明；缺少已录入品类不自动转为购买需求。

验收：每件推荐衣服可定位到真实档案；锁定单品保持不变；不可用单品被排除；候选扫描不逐件弹窗；未知信息不形成虚假承诺；无匹配时明确缺口；预览失败仍保留搭配；图片复核使用所选候选而非整个衣橱。

待确认：首批支持品类、方案数量、排序策略、模型输入限制、延迟和成本预算。验证应包含推荐是否改善实际穿着选择，而不只检查是否成功输出列表。


契约验收补充：M3 有冻结版本及通过校验的边界样例，真实适配未决项明确记录；M5 真实返回通过相同校验。不得以 mock 可用代替真实适配完成。

## 本地资料与执行边界

衣橱筛选、方案编辑、版本、撤销与收藏在本地运行和持久化，断网不丢既有方案。AI 推荐使用用户手动配置的外部接口；候选照片与个人资料提交按 APP 默认允许，限于当前任务所需。测试方案与真实推荐明确区分。

AI 接入方式见 [AI 模型配置与接入](AI模型配置与接入.md)。尚未确定的具体实施选择按 [开发计划](../开发计划.md) 第 13 节在实际遇到时询问项目用户，本轮不做决定。

实现记录（2026-10-29，M3）：手动组合版已落地（无 AI，不宣称智能推荐）——搭配请求/方案结构以业务契约（packages/contract，1.0.0-draft）校验；reason 按缺省语义置空；缺口（missing_category/no_candidate）在界面显式表达；"不同任务如何选择模型"等待 A 线真实输出后确认。

开发待决约定（2026-10-27）：无匹配时“进入补购”仅适用于后期商品模块可用时；首版具体替代入口在 M3 实现时询问项目用户，不自行新增补购模块。 统一询问约定见 [开发计划](../开发计划.md) 第 13 节。

### 基础单品替换与撤销（2026-10-29 修正）

用户明确解锁基础单品后，可将其替换；替换后的单品承接当前方案的基础角色，不自动重新锁定。保存清单须与当前槽位一致，不追加已被替换的原基础单品。撤销同时恢复槽位、基础单品引用、锁定状态及穿法。验收覆盖三件组合替换后仍为三件、连续替换与逐次撤销、非基础单品替换和收藏复用后替换。

### 衣物删除联动（2026-10-29）

已删除或归档单品不能作为新搭配起点或被保存进新方案。收藏复用前检查单品状态，删除标记只供历史展示；当前编辑期间删除了某件衣物，保存时明确拒绝并提示重新选择。
