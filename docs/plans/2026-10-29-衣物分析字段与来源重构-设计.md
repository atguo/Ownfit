# 衣物细节属性与颜色库：设计

日期：2026-10-29（设计已由项目用户确认，含多轮修订）
状态：设计确认，待评审后拆实施计划
关联：[衣橱资料入库与渐进完善](../functions/衣橱资料入库与渐进完善.md)、[基于已有衣橱生成搭配](../functions/基于已有衣橱生成搭配.md)、`packages/contract/src/garmentAnalysis.ts`、`mobile/src/features/sheets/WardrobeItemSheet.tsx`、[衣物 AI 分析分批执行手册](2026-10-29-衣物AI分析-分批执行手册.md)

> 本文只描述设计与边界，不代表已实现。现状以代码为准。
> 本方案**取代**此前"每品类固定字段集 + 枚举选项 + 三态"的草案。

## 1. 背景与目标

真机试用后项目用户提出的问题与需求：

1. 现在**所有品类共用同一套固定 9 字段**（名称/品类/颜色/图案/领型/袖型/版型/标签/描述），鞋、包也套用"领型/袖型/版型"，不相关字段占据界面。
2. 每个字段是"固定选项 + 其他"，"其他"无法记录内容，**丢失细节**。
3. AI 与用户数据只靠一行小字区分，**不能一眼分辨**。
4. 缺少**尺寸测量填写入口**。
5. 希望衣物细节**尽可能详细**（这些数据是给 AI 用的），并且可以**从已有颜色里选配色搭配**。

目标：**放弃固定字段与枚举选项**，改为"AI 按表结构产出细节属性、全部展示、可删、越详细越好"；来源三色可辨；新增测量入口；新增颜色库并接入搭配选配色。

## 2. 设计原则

- **不按固定字段读取/展示**：分析出什么就展示什么。
- **细节优先**：细节越多越好（数据供 AI 使用）。
- **一致性靠引导、不靠强制**：属性名用"推荐键表"引导 AI，契约不限制。
- **事实 / AI / 用户分开**：三色来源可区分，人工值优先。
- **不越红线**：AI 不输出尺寸数字、面料成分、品牌、尺码、真人合身、保暖/防水等结论；尺寸只由用户测量。
- **不臆造**：不确定的属性就不输出，不用空值或猜测填充。

## 3. 数据模型总览

一件衣物的资料分四部分：

1. **内置通用字段**（系统固定，用于分类与基础识别）：`category`（品类）、`name`（名称）、`colors`（颜色）。
2. **动态细节属性**：AI 按需产出的 `{名称, 文本值}` 列表，条数与名称不限。
3. **实测尺寸**：用户录入的测量列表（可空）。
4. **颜色库**（跨单品）：从已确认颜色累积而来，供搭配时选择。

除内置字段外，其余细节均在 `attributes` 表中以"一行一属性"存储；**无 schema 迁移**（沿用通用键值表）。

## 4. AI 输出表结构（契约升为 2.0.0-draft）

```ts
type TargetStatus = 'single' | 'ambiguous' | 'not_garment' | 'unreadable';

type GarmentColor = { name: string; hex: string; isPrimary: boolean };

type GarmentAnalysis = {
  targetStatus: TargetStatus;
  category: GarmentCategory | null;        // 品类（内置）；未确定 = null
  suggestedName: string | null;            // 名称建议（内置）；未确定 = null
  colors: GarmentColor[];                  // 颜色（内置）；0-4 项，非空时恰一主色
  attributes: { name: string; value: string }[];  // 动态细节属性；0-40 项
  unclearParts: string[];                  // 看不清/遮挡说明；0-6 项
};
```

校验规则：

- `hex` 必须为 `#RRGGBB`；`colors` 0-4 项，非空时恰好一个 `isPrimary`。
- `attributes[].name` 1-20 字、`value` 1-200 字；同名不重复；条数 0-40。
- `category` 必须属于七大品类；`suggestedName` 1-30 字。
- `targetStatus !== 'single'` 时：`category`、`suggestedName` 为 null，`colors`/`attributes` 为空，`unclearParts` 至少 1 项。
- 对象严格校验，拒绝未知键。

导出：`garmentAnalysisSchema`、`GarmentAnalysis`、`GarmentColor`、`parseGarmentAnalysis`、各品类的**推荐键表**（见 §8）。

契约版本：`GARMENT_ANALYSIS_VERSION = '2.0.0-draft'`（替换旧的扁平 9 字段形状）。

## 5. 属性展示与交互（单品详情）

- 展示**全部**存在的细节属性，每条一行：`名称：值` + 来源徽章（三色）+ 删除按钮。
- 顺序：先按该品类"推荐键表"的顺序，再把其余属性按写入顺序追加。
- 颜色作为内置字段，展示时也当**一行普通属性**（如"颜色：奶油白（主色）· 米色"），带 hex 色块。
- 名称建议作为一行，用户可采纳为一物名。
- 未知/不适用不再表达：属性存在即"已分析到"，不存在即"未提取"。
- 用户可**物理删除**任一细节属性（见 §9）。

## 6. 三色来源

`attributes.source_type` 扩展为三态，用于区分数据来源：

| 来源 | 含义 | 颜色 |
| --- | --- | --- |
| `ai_inferred` | AI 推断、未确认 | 灰（弱化） |
| `user_confirmed` | 用户点"确认"采纳的值 | 绿 |
| `user_entered` | 用户自己输入/修改/测量 | 主色/强调色 |

判定：点"确认"→`user_confirmed`；手动改/自己填→`user_entered`；AI 未处理→`ai_inferred`；测量→`user_entered`。
色值在实施时从 `mobile/src/ui/tokens.ts` 取或新增三枚来源色。

## 7. 尺寸测量入口（新增）

- 位置：单品详情"实测尺寸"区，替代当前静态"未填写"。
- 内容：可添加多条，每条 = 名称 + 数值 + 单位（默认 cm，鞋可用 mm）+ 可选口径备注；**可空**。
- 名称：按品类给常用建议（上衣/外套：肩宽/胸围/衣长/袖长；下装：腰围/臀围/裤长/裙长；连衣裙：胸围/腰围/裙长；鞋履：内长；包：长/宽/高），也允许自定义。
- 来源：仅用户录入，AI 永不写；写入使 `items.revision` 递增。
- 存储：`attributes` 追加行 `field='measurements'`、`value_format='json'`、`value=JSON.stringify(Measurement[])`、`source_type='user_entered'`；读取取最新一行。

```ts
type Measurement = { name: string; amount: string; unit: string; note?: string };
```

## 8. 推荐键表（引导一致性，不强制）

每品类一份建议属性名清单，用于**提示词引导**与**详情页排序**；AI 可自由增加、契约不限制：

| 品类 | 推荐属性名 |
| --- | --- |
| 上衣 | 领型、袖型、版型、衣长、图案、细节 |
| 下装 | 版型、长度、腰线、图案、细节 |
| 连衣裙 | 领型、袖型、版型、裙长、腰线、图案、细节 |
| 外套 | 领型、袖型、版型、衣长、厚薄、图案、细节 |
| 鞋履 | 鞋型、鞋头、跟型、闭合方式、图案、细节 |
| 包 | 包型、尺寸感、图案、细节 |
| 配饰 | 配饰类型、图案、细节 |

## 9. 数据层变更

- `analysisTypes.ts`：以"动态属性列表"替代固定字段联合类型；`EffectiveAttribute.source` 扩展为 `ai_inferred | user_confirmed | user_entered`；`AnalysisView` 改为 `{ latestTask, lastValidResult, category, suggestedName, colors[], attributes[], measurements[] }`。
- `attributeRepository.ts`：
  - `getAnalysisView(itemId)`：读取全部属性行（动态），按来源与时间解析为列表；内置字段（品类/名称/颜色）单独返回；测量单独返回。
  - `recordUserAttribute`：写单条属性，带 `sourceType`（`user_confirmed | user_entered`）。
  - `deleteAttribute(itemId, name)`：物理删除该名称的属性行，并递增 `items.revision`。
  - 颜色读写（`field='colors'`，JSON）与测量读写（`field='measurements'`）。
  - 版本/删除/stale 保护沿用现有语义。
- `colorLibraryRepository.ts`（新增）：颜色库增删查（见 §10）。
- 删除衣物仍级联清理该衣物的属性与任务（颜色/测量随 `attributes` 一并清理）。

## 10. 颜色库与搭配选配色（新增）

**颜色库**

- 内容：用户已确认过的颜色集合，每条 `{ name, hex, addedAt }`；按 hex+name 去重。
- 写入：当用户确认某单品的颜色时，其颜色并入颜色库（`user_confirmed` 才入库；AI 未确认不入库）。
- 存储：复用 `preferences` 表，`id='color-library'`、`value=JSON.stringify(ColorEntry[])`；**无 schema 迁移**。
- 回显：列表用 hex 显示色块 + 名称。

```ts
type ColorEntry = { name: string; hex: string; addedAt: string };
```

**搭配选配色**

- 在搭配流程提供"从已有配色选择"的入口：展示颜色库（色块+名称），用户选一个/若干作为本次搭配的目标配色。
- 与搭配的绑定方式（筛选候选、记录到方案、或仅作提示）在实施计划中按现有搭配会话结构细化；本设计只确定"入口存在、来源为颜色库"。

## 11. 存储与兼容

- **无 schema 迁移**：`attributes`、`preferences` 均为通用键值表，新键、新 `source_type` 值、颜色库条目都不需改表。
- 历史数据：旧的固定字段行（`neckline/sleeve/fit/...`）作为普通动态属性继续可读可展示；旧 `value_state` 列保留但不再产生新语义（新写入统一 `value_state='known'`、`value_format='text'`，颜色/测量为 `'json'`）。
- 旧的 `Field<T>` 与三态不再使用；契约升 `2.0.0-draft` 替换旧形状，旧 `result_json` 仅作历史诊断读取，不再用于生成视图。

## 12. 非目标

- 不做逐字段并发合并；不做多单品分离；不做面料成分/品牌/尺码表；不做 AI 尺寸推断。
- 不重做搭配契约本身（`CONTRACT_VERSION` 与搭配字段结构不变）；本设计只在搭配流程增加"选配色"入口。
- 不引入后端或云同步。

## 13. 验收

- 契约样例：动态属性（0/多条/超长/重名/未知键）；颜色（hex 非法、无主色/多主色、0 项）；内置字段；非 single 约束。
- 数据层回归：动态属性读取与排序；三态来源判定；物理删除；测量写入/读取；颜色入库去重；stale 与删除保护不变；人工优先不变。
- UI（代码可追）：属性全展示、按推荐键排序；三色徽章；删除；测量可空可填；颜色带 hex 色块。
- 颜色库与搭配：确认后入库、去重、回显；搭配流程可选库中配色。
- 真机：切不同品类；全部属性可见可删；三色可辨；测量可填可空；颜色库选择可用；字体放大与弹层滚动可用。
- 未执行的真机项标"待验收"，不以单测或代码审查代替。

## 14. 待确认项（实施前定，或实施时定）

- 搭配"选配色"与现有搭配会话的绑定方式（筛选 / 记录 / 提示）。
- 三色具体色值。
- 推荐键表的最终措辞（§8）。
- hex 由 AI 给出的准确度边界：仅作近似色块与回显，用户可改。

## 15. 落地批次（建议顺序）

作为新批次推进（接在衣物分析 P0–P8 之后）：

1. 契约重写：动态属性 + 内置字段 + 颜色（含 hex）+ 推荐键表；样例与校验。
2. 提示词重写：按品类引导推荐键、要求颜色给名称+hex、禁止越红线；严格 JSON 解析适配。
3. 数据层：动态属性读写、三态来源、物理删除、测量、颜色库仓库。
4. 单品详情 UI：动态属性全展示、三色徽章、删除、测量入口、颜色行。
5. 颜色库 + 搭配选配色入口。
6. 回归与文档同步（AGENTS、功能文档、手册；真机复验）。
