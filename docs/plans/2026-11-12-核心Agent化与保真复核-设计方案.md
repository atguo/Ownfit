# 核心 Agent 化与保真复核改造——设计方案（2026-11-12）

- 类型：设计方案与分批实施计划（本次仅落库设计，未改代码）。
- 决定状态：D-1～D-3 已经项目用户 2026-11-12 确认；D-4～D-8 为建议默认值，随本方案评审生效或修改。
- 关联：吸收 [M6 实施计划](2026-11-03-M6-真机质量验证与内测候选-实施计划.md) 批次 5 的"模型效果校准"职责（见 D-8）；不撤销既有里程碑验收。

## 1. 核心目标对齐（最高优先级准则）

本改造服务核心能力链路全部四环，其中前两批直接决定"预览可信"这一当前最大可用性缺口：

| 环节 | 本方案的贡献 | 验收证据 |
| --- | --- | --- |
| 1 理解真实衣物 | 入库双层复核：提炼结果对照原照片逐字段判对/错/漏；还原生成抽验直接验证"文字能否还原这件衣服" | 真实衣物错误/遗漏检出一致率；还原抽验区分"提炼不行 vs 生成器不行"的案例 |
| 2 基于衣橱推荐 | AgentRun 编排：入口（选一件/空手）→ 多轮推荐 → 自动采用 → 自动预览 | 真机一键链路走查（组合、锁定/替换仍归用户、消耗如实展示） |
| 3 本人上身预览 | 相似度评分 + 阈值硬门控：达标才呈现，未达标如实报告原因与分数 | 真实样本人工判定与核对器分数的一致率、达标率报告 |
| 4 穿着反馈 | 本次不含（登记待确认项 T-1 反馈回流） | — |

定位一句话：把现有"管道 + 软门禁"改成"agent 编排 + 硬门控"。守门机器（快照、revision、CAS、状态机）全部保留复用；新增的是编排层、复核阶段、评分门控与成本台账。

## 2. 现状判定与根因（为什么改）

### 2.1 架构现状判定

当前实现是"任务内有微型闭环、任务间由用户手动编排"：推荐/预览/分析各有状态机、不可变输入快照与本地校验，但模型每步单次调用，跨任务无控制器，反馈不回流（`worn_records` 仅用于方案列表状态展示，不进推荐输入）。

### 2.2 "预览后衣服完全变另一套"的四层根因（代码可证）

1. **生成端（结构性）**：MiniMax `image-01` 的 `subject_reference` 仅支持人物肖像（A 线实验结论），衣物一致性完全靠文字提示词；一次生成需同时绑定多件衣物的颜色/图案/领袖/版型/穿法，多目标属性绑定是此类模型的系统性弱项。
2. **输入端**：预览吃的衣物特征是照片提炼的文字（A2 特征视图），提取质量从未校准（M6 批次 4 登记"模型识别质量待校准"）。提炼漏项/错项时预览必然跑偏，且无环节验证提炼结果能否"还原"原衣物。
3. **核对端（软门控）**：C8 核对器（`mobile/src/services/ai/previewChecker.ts`）已实现，但是三级判定（match/minor/major）而非相似度分值；未经真实样本校准；判成 major 也照常显示图片，仅加警示文字、挡比较入口（`PreviewSheet.tsx` 的 `compareSelectable` 逻辑）。
4. **纠偏端**：重大偏离至多自动纠偏一次，且纠偏提示词只重申快照内已有文字证据（`buildCorrections`），对生成器系统性弱项收效有限。

结论：现有链路是"如实标注问题"，不是"拦截问题"。第 1 批把第 3 层升级为数值评分 + 硬门控，并用真实样本校准（效果优先，见 §6）。

## 3. 目标架构

```
入口：用户选一件衣服（choose 页 / 衣橱"围绕这件搭配"）/ 空手"给我配一套"
 └─ AgentRun（新编排层：持久化状态机，可中断恢复、幂等、防重复计费）
     ├─ 资料库读取：衣橱快照 / 个人资料 / 长期偏好 / 天气时效校验
     │   （复用现有：loadWardrobeProfile、loadSceneSnapshot、getBodyProfile、
     │     getPreferences、isRealWeatherUsable、输入快照 V2 与指纹机制）
     ├─ 推荐阶段：多轮（生成 → 本地硬校验 → 对照场景/锁定/缺口/多样性自评 → 修订），
     │   轮次预算内（D-7）；产出候选 + 自选最优
     ├─ 采用阶段：自动采用最优候选进 outfitSession（锁定/替换/撤销仍归用户，不改变控制权）
     ├─ 预览阶段：自动入队 → 生成 → 条件提交 → 相似度门控（数值评分 + 阈值）
     │    └─ 未达标 → 有界纠偏（仍至多 1 次）→ 仍未达标 → 不呈现，如实报告分数与原因
     └─ 呈现阶段：组合 + 通过门控的预览（分数）+ 未通过原因 + 其余候选（文字/缩略图）+ 本次消耗
 成本台账：每次外部调用记轮次/用量/成败；单次运行预算封顶，超限停链如实报告
```

入库侧（第 2 批）在 `garmentTaskRunner` 分析提交后追加复核阶段：

```
照片 → AI 分析（现状） → 层1 对照复核（必做）：原照片 vs 提炼结果 → 逐字段对/错/漏 + 缺失关键特征
                      → 层2 还原生成抽验（可开关，默认开发期开）：提炼特征 → 重新生成该件衣物图
                        → 视觉比对原图 vs 生成图 → 相似度分（诊断"提炼不行"还是"生成器不行"）
```

## 4. 三批实施计划（D-3：先保真后链路）

### 第 1 批：预览相似度门控 + 真实样本校准

目标：让"呈现出来的预览"可信——未达标的图不再冒充结果。这是 agent 链的验收前提。

工作项：

1. **核对器 v3（数值评分）**：`previewChecker.ts` 升级，规则版本 `PREVIEW_CHECK_RULE_VERSION` v3。每件衣物输出 `score`（0–100）+ 偏离维度标记（颜色/图案/关键特征/穿法/漏件/换件；漏件或整件被换 = 0 分）；人物一致性单独一条；`overall_score = min(各单件 score)`（最严口径：任一件不达标即整图不达标）。保留三态判定用于兼容旧记录。
2. **schema v9**：`preview_checks` 增 `overall_score`、`item_scores`（JSON）、`rule_version` 列；迁移沿用 `user_version` 事务惯例，旧记录分数为 NULL 按旧三态口径展示。
3. **硬门控**：呈现层只把"核对完成且 overall_score ≥ 阈值"的图作为预览结果；未达标显示"未通过"卡片（分数 + 偏离明细，开发期可展开查看原图对比，用于校准）。`unknown`（缺图/核对失败/无法判断）= "未能核对"，不算达标、不触发自动纠偏（沿用现有语义）。阈值进 `/dev` 设置页，默认 80（D-4）。
4. **纠偏增强**：`buildCorrections` 从"重申证据"升级为"逐件指出偏离维度 + 强调必须还原"；纠偏次数仍至多 1 次。
5. **真实样本校准（吸收 M6 批次 5）**：用项目用户真实衣橱 + 人物参考，N ≥ 10 个组合生成预览，人工逐张判定"可呈现/不可呈现"，对照核对器分数：量出错分率与达标率，据此调阈值与提示词；结论登记校准报告（本目录）。**若达标率过低（建议触发线：可呈现图的 overall_score 中位数 < 阈值，即门控基本全拦），启动生成模型更换评估**（如支持衣物参考图输入的图像模型）——用户已确认"以后可通过换模型减少误差"，本批给出量化触发条件。

验收：校准报告（人工判定 vs 分数一致率、达标率）；自动回归（假客户端，评分解析/门控/迁移/兼容旧记录）；真机走查（未通过卡片、阈值调整、纠偏文案）。不以测试全绿替代模型效果结论。

### 第 2 批：入库双层复核

目标：拦住"提炼结果本身不还原原衣物"——预览保真的输入端前提。

工作项：

1. **层 1 对照复核（必做）**：分析提交后自动入队复核后处理（生命周期仿 `preview_postprocess`：queued/checking/done/interrupted，中断不自动重发）。1 次视觉调用：原照片 + 提炼结果（A2 特征视图文本）→ 逐字段 `正确/错误/遗漏` + 缺失关键特征清单。规则版本化。
2. **schema v10**：`garment_reviews` 表（item_id、analysis_task_id、layer、verdicts JSON、rule_version、状态与时间戳）。
3. **详情页呈现**：复核状态行；判错/遗漏字段在 `WardrobeItemSheet` 高亮提示用户确认修正；复核通过的来源标记保持现状（不新增确认负担，符合"易上手"约束：复核是 AI 对 AI，不逐项打扰用户）。
4. **层 2 还原生成抽验（可开关，默认开发期开）**：dev 设置全局开关；入口 = 单件详情页"验证还原效果"手动触发 + 开关开启时新入库衣物自动触发。流程：提炼特征 → 图像生成单件衣物图 → 视觉比对原图 vs 生成图 → 相似度分。落库 `garment_reviews`（layer=2）。
5. **校准**：真实衣物 M ≥ 10 件，人工对照复核的检出一致率；还原抽验至少产出"提炼问题"与"生成器问题"各一个可归因案例。

验收：检出一致率报告；自动回归（后处理状态机、中断恢复、开关行为、迁移）；真机走查（复核状态、手动抽验入口）。

### 第 3 批：AgentRun 编排链 + 成本台账

目标：一条入口动作串起"配一套 → 采用 → 预览 → 门控呈现"，全程预算封顶、可中断恢复。

工作项：

1. **编排层**：新模块 `mobile/src/services/agent/`（orchestrator + run store）。schema v11：`agent_runs`（入口、场景快照、阶段状态机 assembling/recommending/adopting/previewing/gating/presenting/终态、预算与消耗、产出）与 `agent_call_log`（run_id、kind=text/vision/image、用量、耗时、成败）。
2. **推荐多轮**：`recommendationService` 增自评轮——第一轮候选 → 本地校验 → 自评（对照约束清单挑毛病：场景匹配/锁定完整/缺口如实/候选差异）→ 第二轮修订；总轮次 ≤ 2（D-7）。执行仍走现有任务状态机与快照复核，AgentRun 只编排不绕过。
3. **自动采用 + 自动预览**：采用走现有 `evaluateAdoption` 复核（基线变了就停链如实报告）；预览自动入队 1 张（D-2），沿用条件提交与门控。锁定/替换/撤销仍归用户（outfitSession 不变）。
4. **成本台账**：openai 兼容调用记录返回 usage（无 usage 的调用记次数与耗时）；单次运行预算默认 text ≤ 4 次、vision ≤ 6 次、image ≤ 2 次（D-7，dev 设置可调）；超限停链，呈现页如实显示"已达预算上限"与已消耗。
5. **入口改造**：choose 页"AI 帮我搭一套"与衣橱"围绕这件搭配"升级为 AgentRun 入口；新增空手入口（无 basis，全柜组合）。呈现页在 outfit 页：组合、预览通过状态与分数、其余候选、本次消耗。
6. **中断恢复**：启动恢复把在途 run 标 interrupted，可从断点阶段续跑（幂等，防重复计费：沿用 CAS/状态机语义；续跑前重校验快照）。

验收：真机一键链路走查（含未达标如实报告、预算封顶触发、中断后续跑）；自动回归（状态机、幂等、台账记账）；真实模型效果沿用第 1/2 批校准结论，不重复宣称。

## 6. 成本控制口径（用户 2026-11-12 指示）

- 开发阶段第一优先级是效果，成本优化在效果达标后进行。
- 本方案先做简单控制：轮次封顶（D-7）+ 每次调用用量记账（`agent_call_log`），不做复杂预算调度。
- 高成本点排序：图像生成 > 视觉核对 > 文本。D-2（只自动生成 1 张）与 D-6（抽验可开关）即为控制点。

## 7. 风险与未验证边界

1. **生成模型可能根本不达标**：若第 1 批校准显示文字路径达标率过低，硬门控会"诚实地什么都呈现不了"——此时正确动作是评估更换图像生成模型（触发条件见第 1 批第 5 项），不是放宽阈值。这是本方案显式接受的中间状态：不可用的诚实呈现优于可用的虚假呈现。
2. **核对器自身误判**：评分门控把核对器从"参考信息"升级为"唯一裁判"，其误判直接影响呈现率；v3 规则版本化 + 校准报告是对策，阈值可调是开发期逃生口。
3. **真实模型费用**：校准（N≥10 组合 + M≥10 件衣物）与还原抽验均产生真实费用，由项目用户执行与核验（沿用既有边界：agent 不代付、不代验效果）。
4. **本方案未实施**：以上均为设计，代码现状以 AGENTS.md 第 1 节为准；各批实施时按第 6 节文档义务同步。
