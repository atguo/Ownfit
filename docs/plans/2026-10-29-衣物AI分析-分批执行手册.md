## 0. 先读这段，不要重新设计

你的任务是按本手册实现衣物照片分析，不是重新做方案评审，也不是实现完整 M4/M5。

“DeepSeek 4.1 Flash”指执行代码任务的模型，不是 APP 指定的服装分析模型。APP 只能调用用户已有配置中支持图片理解的模型，不得硬编码任何供应商、model ID、URL 或 Key。

用户已确认：新照片保存后自动分析，旧衣物由用户手动补分析。保留这一行为，不得为了容易实现改成全部手动。

技术默认项尚未获单独实施批准：D1=多个模型选择并记住，默认失效不自动换服务；D2=发送前配置变化 blocked，已发送请求沿用快照；D3=90 秒超时、无自动付费重试、中断手动重试，客户端取消不保证退款。P0 汇报时一次列出这三项。P4 前须确认用户明确同意这些默认项；没有同意就只询问一次，不自行解除功能文档中的待决事项。用户可一次批准 D1-D3，不需要每批重复询问。计划编写、P0 核对或 P1 契约授权不等于批准 D1-D3。

本手册是本任务唯一执行入口；[原计划](2026-10-29-衣物AI分析接入计划.md)仅供背景阅读，不再从原计划额外派生任务。根目录 AGENTS、mobile/AGENTS 和归属功能文档仍然有效。发现本手册与上级规则或用户新决定冲突时停止相关部分，说明冲突，不自行选一个覆盖另一个。

## 2. 固定业务规则

下面的 R 编号是验收依据。测试和代码说明应引用编号，不自行改写规则。

### R1. 触发与模型

- 新照片：成功建草稿后自动分析，保存照片不能等待 AI。批量照片只进行一次模型选择/缺配置提示。
- 旧衣物：详情手动分析；衣橱批量入口只处理 draft/active、有主图、从未创建任务的衣物。
- 归档衣物只看结果，恢复后可分析。失败/中断/过期不随批量入口自动重试。
- 可用候选：openai + vision + 非空 model ID/有效基础地址 + 可读取密钥。MiniMax 图像生成不参与。
- 首次一个候选直接使用并记住；多个候选选择并记住。已有默认失效时即使只剩一个候选，也要求确认新模型，不能静默切供应商。
- 无配置提供“去配置/暂不分析”；密钥缺失、配置损坏分别提示，不能全归为“未配置”。
- 去配置后回到仍存在的录入会话，继续未发送的本批；会话已退出则不偷偷扫描旧草稿。

### R2. 人工资料与输入版本

- 正式名称和品类不会被后台 AI 改写。草稿仅对未编辑字段预填建议；入库仍须用户确认。
- 所有 AI 属性自动保存为未确认推断，允许逐字段确认/修正，不新增逐项必审流程。
- 最新人工确认优先，人工确认的 unknown 也优先。新 AI 结果不能替换人工值。
- 同一当前照片，使用最新成功任务的 AI 属性；最新成功为 unknown 时不能回退旧值冒充新值。
- 新任务失败保留上次成功结果，页面同时显示本次失败和旧结果时间。
- 用户修改或确认入库使 revision 增加。在任务发送前发现 revision/照片变化：stale，零网络请求。在返回时发现变化：stale，不应用。
- 采用保守的整次结果过期策略，不实现逐字段并发合并。分析期间手动入库可能需要重新分析，UI 必须解释原因，不静默付费重跑。
- 已经保存的结果不会仅因后续修改无关字段而被删除；照片换掉时不能继续把旧图推断当作当前结果。

### R3. 网络与隐私

- 每次请求只发送本件原件副本、必要类别提示及提示词。用 JPEG data URL，不发送 file URI。
- 分析 max_tokens=2048、timeoutMs=90000、并发=1；连接测试仍是 16/30000。参数是开发默认，不是准确率或服务保证。
- 只允许完整 JSON 对象，或整体包在一层 ```json 围栏中的对象；禁止截取首尾花括号“修复”任意文本。
- 不额外调用模型修复 JSON，不自动重试网络/无效结果，不把供应商错误正文原样写库。
- 照片不整库上传；Key 只在请求期间从安全存储读取。数据已发送后无法承诺撤回、取消计费或退款。
- 改正“照片不会上传”和“后续版本才有解析”的旧文案。

### R4. 任务与恢复

- 页面不拥有执行器。根布局启动模块单例，串行领取任务，StrictMode 重挂载不重复启动。
- queued 在发送前写库；领取后先写 running 再发请求。数据库事务中不得等待网络。
- 切后台不领取新任务；进行中的请求尽力完成，不承诺系统持续执行。
- 启动时遗留 running -> interrupted，禁止重发；queued 复核有效后可继续。
- failed/interrupted/stale/blocked/cancelled 均不自动重跑；手动重试创建新任务，并保留 retry_of_task_id。
- 同一衣物最多一个 queued/running；重复点击返回已有任务。相同 request_key 只对应一个任务。
- 任务创建失败：照片仍保存，提示“分析未开始”。不是整个入库失败。
- 有结果但提交失败：内存保留结果，展示“结果保存失败/重试保存”；仅重试本地提交。强杀丢失未落盘结果则 interrupted。

### R5. 配置变化与删除

- 创建任务时固定配置快照；发送前比较当前调用配置版本，不同或已删除则 blocked，不改目的地址。
- 发送后编辑/删除配置不改变已发送请求，已有返回仍按衣物版本检查；无法撤回外部服务已经接收的数据。
- 归档：queued/running -> cancelled，保留旧成功结果；恢复不自动重新分析。
- 彻底删除：资料事务内删除 attributes 和 tasks，再沿用文件删除流程；保留现有 deleted 标记与收藏/穿着记录。
- 晚返回只允许 UPDATE 已存在且 running 的任务。衣物 deleted 或任务不存在，直接丢弃，不 INSERT/UPSERT 复活任何结果。
- 请求 AbortController 只用于尽力停止；最终安全性依赖数据库状态检查。

## 3. 固定技术规格

### 3.1 分析契约

新增 `packages/contract/src/garmentAnalysis.ts`；独立版本 `GARMENT_ANALYSIS_VERSION = '1.0.0-draft'`。保留既有搭配版本和行为，不升级整个搭配契约来凑分析字段。

属性结构固定如下。只对下表属性套 Field，targetStatus 和 unclearParts 不套：

```ts
type Field<T> =
  | { state: 'known'; value: T }
  | { state: 'unknown'; value: null }
  | { state: 'not_applicable'; value: null };
```

| 键 | known 值 | 其他限制 |
| --- | --- | --- |
| suggestedName | string | 1-30 字；仅 known/unknown |
| category | 上衣/下装/连衣裙/外套/鞋履/包/配饰 | 仅 known/unknown |
| colors | `{ name: string; isPrimary: boolean }[]` | known 时 1-4 项，名字 1-20 字，恰有一个主色；仅 known/unknown |
| pattern | 纯色/条纹/格纹/印花/拼接/其他 | 可 unknown/not_applicable |
| neckline | 无领/圆领、V领、立领、翻领、连帽、一字领、其他 | 可 unknown/not_applicable |
| sleeve | 无袖/短袖/七分袖/长袖/其他 | 可 unknown/not_applicable |
| fit | 修身/合体/宽松/oversize | 可 unknown/not_applicable；不是真人合身 |
| stylingTags | string[] | 0-6 项，每项 1-20 字；仅 known/unknown |
| description | string | 1-120 字；仅 known/unknown |

顶层还必须有 `targetStatus: 'single' | 'ambiguous' | 'not_garment' | 'unreadable'`、`unclearParts: string[]`（0-6 项，每项 1-80 字）。所有键必需，对象严格校验，未知键拒绝。非 single 时所有 Field 必须 unknown，unclearParts 至少 1 项。

提示词明确禁止精确尺寸、面料成分、品牌、尺码、真人合身和确定保暖结论。合同校验不能保证模型不幻觉；真机仍逐项核对。实验中的“鞋”只在供应商适配器中显式映射为“鞋履”，正式契约只接受“鞋履”。

导出：`garmentAnalysisSchema`、`GarmentAnalysis`、`parseGarmentAnalysis(value: unknown)`，返回 `{ok:true,value}` 或 `{ok:false,error}`，沿用 contract 包现有风格。

### 3.2 schema v3 与记录编码

只增加以下结构，不创建第二套分析库：

- items：`revision INTEGER NOT NULL DEFAULT 1`。
- attributes：`value_state TEXT NOT NULL DEFAULT 'known'`、`value_format TEXT NOT NULL DEFAULT 'text'`、`analysis_task_id TEXT`。旧 value 为 NULL 的行回填 unknown。
- tasks：下表。仅 kind=garment_analysis，不实现其他 kind 的执行。
- ai_task_preferences：`kind TEXT PRIMARY KEY`、`default_config_id TEXT NOT NULL`。

| tasks 列 | SQLite 类型及规则 |
| --- | --- |
| id | TEXT PRIMARY KEY |
| kind / item_id / status | TEXT NOT NULL |
| input_revision / attempt | INTEGER NOT NULL；attempt 从 1 开始 |
| photo_id / input_key / request_key | TEXT NOT NULL；request_key UNIQUE |
| config_id / config_snapshot / config_revision | TEXT NOT NULL；snapshot 是白名单 JSON |
| contract_version / prompt_version | TEXT NOT NULL |
| retry_of_task_id | TEXT，可空；删除衣物时全部清理，不依赖外键自动级联 |
| result_json / error_kind / error_summary | TEXT，可空 |
| created_at / updated_at | TEXT NOT NULL，ISO 时间 |
| started_at / finished_at | TEXT，可空 |

索引：tasks(item_id,created_at)、tasks(status,created_at)；部分唯一索引 tasks(item_id)，条件 `status IN ('queued','running')`。迁移沿用旧表，不触碰收藏表结构。

status 只能取 queued/running/succeeded/failed/interrupted/stale/cancelled/blocked。成功解析但 targetStatus 非 single：任务 succeeded，保存诊断 JSON，不写属性，界面显示“需要清晰单品照”，不显示“已识别衣物”。

编码固定：字符串使用 value_format=text；数组用 JSON；unknown/not_applicable 的 value=NULL。AI source_type=ai_inferred、confirm_status=unconfirmed、source_ref=photo_id、analysis_task_id=task.id、item_version=input_revision。人工新增记录沿用 user_confirmed/confirmed，source_ref 写确认或修正的入口。

同批记录顺序用现有 recorded_at 加 SQLite rowid 作稳定排序，不仅用可能相同的时间戳。AI 查询先确定最新成功任务，再取该任务的属性，不逐字段拼接多次模型输出。

config_snapshot 只含 id/name/urlKind/baseUrl/modelId；密钥与 keyRef 不放 snapshot。`input_key` 是包含 itemId/revision/photoId/configId/config_revision/contractVersion/promptVersion 的固定顺序 JSON 字符串，不需要密码学哈希。

config_revision：在现有 ModelConfig 增加可选 `callRevision: string`。旧配置缺省为 'legacy'；新增配置生成随机版本；URL 类型/地址/model ID/能力标签/密钥变化时生成新版本，名称或连接测试变化不更新。Key 变化也必须能使 queued 任务 blocked，不读取 Key 计算哈希。

### 3.3 事务与模块责任

- db.ts 导出可测试的迁移函数；getDb 仍负责 SQLCipher 打开和密钥。迁移函数不依赖真实设备 Key。
- v3 schema 与 user_version 在同一事务。当前安装的 Expo 支持时使用 exclusive transaction 和其 tx 对象执行本任务短事务；先核对类型签名，不用普通异步事务让网络/其他写入意外参与。
- attributeRepository：人工属性写入和展示取值。taskRepository：任务、默认模型、原子提交。itemRepository：revision、人工基础字段、归档/删除。repository 不导入 UI 或网络执行器。
- garmentTaskRunner：编排 repository 与模型客户端；仅它发起分析执行。UI 不能直接调用 fetch。
- garmentAnalysisStore：订阅变化通知与当前会话待提交 ID；不是持久化真源，不存 Key，不保存第二份权威结果。
- 删除安全不依赖通知是否收到。通知仅用于主动 abort 和 UI 刷新，提交时状态检查必须独立存在。

固定接口名和职责，参数可补充必要静态类型，不改变语义：

| 接口 | 输入/输出及约束 |
| --- | --- |
| resolveVisionConfig | 返回 ready(config)、choose(candidates)、missing、invalid(reason)；不发网络请求 |
| enqueueGarmentAnalysis | 输入 itemId/configId/trigger/requestKey/retryOfTaskId?；返回 created(task) 或 existing(task) 或 rejected(reason) |
| runGarmentAnalysis | 输入已校验照片和配置快照、signal；返回业务分析或结构化错误，不写 DB |
| commitGarmentAnalysis | 输入 taskId/result；返回 applied、stale、discarded 或抛本地保存错误；不重新调用 AI |
| getAnalysisView | 输入 itemId；返回最新任务、当前照片的上次有效结果、人工优先属性 |

跨批类型由 P2 新增 `mobile/src/data/repositories/analysisTypes.ts` 统一导出，仅依赖 contract 的类型，不依赖 UI、配置存储或执行器。P2 固定以下形状，后续不得各自创建同名不兼容类型：

```ts
type AnalysisTrigger = 'auto' | 'batch' | 'manual' | 'retry';
type RejectReason =
  | 'item_missing' | 'item_unavailable' | 'photo_missing'
  | 'config_missing' | 'config_invalid' | 'config_changed'
  | 'retry_target_invalid';
type AnalysisFieldKey =
  | 'suggestedName' | 'category' | 'colors' | 'pattern'
  | 'neckline' | 'sleeve' | 'fit' | 'stylingTags' | 'description';
type EffectiveAttribute<K extends AnalysisFieldKey> = {
  value: GarmentAnalysis[K];
  source: 'user_confirmed' | 'ai_inferred' | 'none';
  recordedAt: string | null;
  analysisTaskId: string | null;
  aiSuggestion: GarmentAnalysis[K] | null;
};
type AnalysisView = {
  latestTask: AnalysisTask | null;
  lastValidResult: {
    taskId: string; result: GarmentAnalysis;
    completedAt: string; modelName: string;
  } | null;
  attributes: { [K in AnalysisFieldKey]: EffectiveAttribute<K> };
};
```

`AnalysisTask` 按 3.2 tasks 列映射为 camelCase，日期和状态类型固定；不得包含 Key。无任何属性记录时 value=unknown/null、source=none。数据库异常抛出供 UI 明示，不伪装成空结果或业务 rejected。
