# 天气与场景适配

版本：v0.3｜设计草案｜2026年10月26日  
所属项目：[项目计划书](../项目计划书.md)

## 1. 功能目标与问题

让穿搭适合实际出行环境与活动，避免推荐只好看却过冷、过热或不适合雨天。季节标签不能代替当天条件。

## 2. 范围与边界

在生成搭配前提供环境约束与排序依据，支持自动天气和手动输入。负责穿着适配，不负责通用天气应用或单品资料采集。

## 3. 使用场景与流程

选择目的地、日期和时段 → 授权位置或手动选择 → 获取天气 → 补充场景与室内外安排 → 结合个人体感 → 将约束交给搭配功能 → 实际穿着后通过反馈修正。

如“明天上班，主要在办公室，晚上步行回家”，需要同时考虑室内环境和晚间出行，而不是只读取当日最高温度。

## 4. 关键设计与理由

| 条件 | 对推荐的影响 |
| --- | --- |
| 地点、日期、时段 | 对应实际活动的天气 |
| 气温、体感温度 | 厚薄、露肤与保暖 |
| 昼夜温差 | 可穿脱叠穿 |
| 降雨、风力 | 鞋履、外层、防风防雨需求 |
| 室内外、空调、活动场景 | 调整不同环境间的穿法 |
| 季节 | 辅助参考，不覆盖具体天气 |
| 怕冷怕热与历史反馈 | 个性化调整 |

按整套穿法评估，不把某件衣服简单限定为只能在某个季节使用。未知面料或结构不能形成已确认防水、保暖结论；适配分数或温度阈值必须经验证后再定义。

### 4.1 默认提供帮助，允许快速纠正

已确认：记住用户常用地点与场景，在请求中展示可修改摘要，如“今天通勤，白天在室内，晚上可能需要外套”。用户可快速改为全天户外、其他城市或不同日期，不必每天填写完整表格。

常用场景只是默认值，不能当作当日已确认事实；当次调整不自动覆盖长期默认。显示与当前请求一致的地点、时间和场景，避免隐藏旧条件。

### 4.2 解释对搭配的具体影响

结果说明天气引起的实际选择，如“增加可脱外套以应对晚间降温”，而不是仅展示气温。缺乏相关资料时说明限制，不虚构保暖、防水属性。

偏冷、偏热反馈结合空调、活动强度、室内外和个人体感分析，不能全部归因于气温。反馈上下文与归因按反馈文档维护。

## 5. 数据与状态

输入包含用户选择的地点、日期、时段、活动与体感偏好。环境记录保存来源、获取时间、适用时段、数值与单位，区分服务数据和手动输入。

输出为本次搭配的环境条件、建议、依据与缺口。区分尚未获取、可用、失败或不适用时段；具体过期判定待服务选型后确定。

## 6. 异常与替代路径

拒绝位置授权可手动选地点。服务不可用、目标日期超出预报范围或数据已失效时，提示实际状态，允许手动填写，不能把历史或猜测数据展示为实时预报。

缺少衣物证据时依照衣橱规则按需补充，或提供一般搭配并说明限制。用户改变地点、日期或时段后重新检查环境，不能静默沿用旧条件。

## 7. 功能依赖

[个人资料](个人资料管理.md)提供体感偏好；[衣橱](衣橱资料入库与渐进完善.md)维护厚薄、结构和来源；[反馈](穿着反馈与搭配收藏.md)提供真实环境感受；[搭配生成](基于已有衣橱生成搭配.md)和[商品匹配](灵感搭配与商品匹配.md)消费环境约束。

## 8. 验收条件与待确认事项

新增验收：默认场景可见且可修改；当次变更不静默改长期默认；地点或时段改变后摘要和推荐同步复核；用户能理解环境条件具体影响了哪个穿着选择。

验收：天气在推荐前参与判断；手动与服务数据可区分；更改时空条件会复核；拒绝定位仍可使用；获取失败不伪造；整套冷热反馈不自动归因到每件单品。

待验证：天气服务、覆盖地区、刷新与失效策略、适配方法、个人体感如何影响排序，以及不同环境下推荐的实际舒适度。

## 本地资料与执行边界

场景、体感偏好及最近天气记录在本地保存。自动天气是可选联网能力，查询仅发送必要的城市/地区和时段，不发送衣橱或人物资料；定位需单独授权，可手动选城市。断网或拒绝权限时可编辑天气与场景，不依赖自有服务器。
