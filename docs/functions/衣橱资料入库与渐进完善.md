# 衣橱资料入库与渐进完善

版本：v1.5｜开发指南｜2026年10月26日  
所属项目：[项目计划书](../项目计划书.md)

## 1. 功能目标与问题

解决逐件测量、拍照和描述导致的录入负担，在不伪造资料的前提下建立可信、可复用的衣物档案。原则是先保存、后完善，按当前用途补充，事实、推断与未知分开。

不要求每件衣服达到统一完整度，不以填满字段作为使用门槛。把工作分散到需要它的时候，同时保持每一种输出所需的证据标准。

## 2. 范围与边界

负责轻量入库、商品资料导入、结构化提取、用途可用性检查、补充节奏与衣物版本维护。反馈的交互与归因集中在[穿着反馈与搭配收藏](穿着反馈与搭配收藏.md)，本人图像生成与真实性验证归[AI上身预览](AI上身预览.md)。

本功能规定产品行为；模型图片规格、各品类合身判断与质量阈值待实验。资料满足输入要求不等于生成结果已达到实际试穿精度。补充频率等数值是开发默认，需使用测试验证。

## 3. 使用场景与流程

### 3.1 总体流程

提供一张图片或商品来源 → 保存草稿 → 确认单品与大类 → 完成轻量入库 → 后台提取资料 → 参与候选筛选 → 被选入具体搭配 → 检查本次用途所缺证据 → 少量补充或选择替代路径 → 生成结果 → 穿着时自愿反馈 → 持续修正。

所有补充均写回原单品档案并复用。不能每次生成重复要求同一份资料，也不能因为某个字段缺失而要求重做整套录入。

### 3.1.1 从一次搭配任务开始

已确认：首次入口以“你想先搭配哪一件？”展开。先录入目标单品，再按本次组合需要引导添加少量其他衣服。例如录入一条裤子后，添加两件上衣和一双鞋即可尝试生成；这是示例，不是数量门槛。用户无需先建立完整衣橱，已有足够资料时立即进入搭配。

系统发现缺少某类单品时，应表述为“已录入的衣橱中暂未找到”，不能推断用户没有。提供“添加我已有的”“暂时不搭配这一类”等路径；后期商品功能可用后，再提供“寻找新商品”。用户暂不添加鞋子时，可输出已覆盖部分并标明范围，不虚构完整组合。

首次体验依次围绕锁定单品、添加必要候选、获得方案、局部调整与按需预览推进。资料补充仍遵循统一频率规则，不借首次引导集中索要全部资料。

### 3.2 首次录入的最少信息

“保存草稿”与“可参与搭配”分开，避免解析失败造成已输入内容丢失。

| 信息 | 保存草稿 | 轻量入库并参与基础搭配 | 获取方式 |
| --- | --- | --- | --- |
| 至少一个来源 | 必需：照片、截图或商品链接之一 | 保留来源 | 用户本地选图或粘贴 |
| 可对应到这件衣服的主图 | 可暂缺，例如链接尚未解析 | 必需：能辨认单品整体外观；不要求一次拍齐背面与细节 | 实物照片，或用户确认对应款式与颜色的商品图 |
| 单品身份 | 可待确认 | 必须确认图中哪一件是要录入的衣服；多人或多单品图需选中目标 | 系统框选，用户确认或修正 |
| 品类大类 | 可未知 | 必需，例如上衣、下装、连衣裙、鞋、包；不强迫选择细分类 | AI 预填，用户确认 |
| 所属与使用状态 | 标记为草稿 | 加入衣橱表示用户声明已拥有；默认可用并允许修改 | 无须再增加独立问卷；待购商品存入候选区 |
| 主色、图案、领型等外观属性 | 非必填 | 能识别则保存推断；不确定则留空，不阻止入库 | AI 后台提取，不要求逐项审核 |
| 名称、品牌、标注尺码 | 非必填 | 非必填 | 名称可自动生成；品牌与尺码后续导入或填写 |
| 实测尺寸、面料、细节照、上身照、体感描述 | 非必填 | 非必填 | 后续按用途补充 |

首次交互默认只做“提供来源 → 确认目标单品与大类 → 保存”。不要同时要求测量、拍背面、拍吊牌和填写体感。个人身材资料也不作为衣服入库的前置条件。

主图存在严重遮挡或无法辨认目标时，仍可保存草稿，但暂不进入需要外观证据的推荐。链接解析失败时保留链接与输入，提示可改用截图或拍照，不要求从头开始。

### 3.3 录入入口

#### A. 实物拍照

1. 用户拍摄或选择一张能看清整体的照片。
2. 系统检查目标是否清楚，必要时提示一次具体问题，例如“下摆被裁掉”。用户可重拍或先存草稿。
3. AI 提议品类与目标范围，用户确认后完成入库。
4. 其余可见特征后台提取；无需等待所有解析完成才保存。

#### B. 商品链接、订单截图或吊牌

1. 尝试获取商品资料，展示匹配到的款式与颜色，支持用户纠正。
2. 若截图或链接中有多个商品，先选择目标；不自动把订单里所有商品加入衣橱。
3. 有明确尺码时请用户快速确认；没有时可跳过。未确认尺码前不绑定某一行尺码表为这件衣服的尺寸。
4. 商品图足够清晰且对应款式与颜色已确认时，可直接用于轻量入库，不强制再拍实物。
5. 后续涉及实物色差、缩水、改短或细节不一致时，再补实物资料。

不能仅靠吊牌推断完整外观；只有吊牌且无主图时先存草稿。无法获取商品资料时，不臆造尺寸与面料。商品尺码表始终标注为品牌资料。

#### C. 批量照片或日常穿搭照

支持批量保存草稿和逐件快速确认。系统可提议从穿搭照中分出多个单品，但用户确认前不自动认定所有单品均属于用户，也不将遮挡部分补画后当作原始证据。

复用同一张照片时保留原图及每件衣服的区域引用。疑似重复单品提示用户选择复用或新增，不静默合并不同颜色、尺码或同款的两件实物。

## 4. 关键设计与理由

### 4.1 按用途判断可用性

每次请求根据“目标用途 + 当前单品 + 已有证据”判断条件，不以全局分数决定是否可使用。

| 用途或触发时机 | 最少需要的证据 | 缺失时补什么 | 用户跳过后的行为 |
| --- | --- | --- | --- |
| 浏览、收藏、历史记录中引用 | 单品 ID；草稿可显示占位信息 | 不主动追问 | 正常查看，显示待完善状态 |
| 进入后台候选池 | 已完成轻量入库、当前可用 | 优先后台解析主图；不因被扫描到就弹窗 | 未知属性不能被当成确定不匹配；无法确认的关键限制不承诺满足 |
| 用户锁定单品生成穿搭 | 已确认目标与大类、可辨认主图 | 仅在主图不足或身份有歧义时补图、选目标 | 保存请求，允许换单品；不要求全套尺寸 |
| 被选为搭配候选 | 能复核外观与组合关系 | 先复用已有图；只有选定后确实需要时再问 | 可选其他证据足够的单品，不打断候选筛选 |
| 生成本人视觉预览 | 当前套装每件衣服有足够视图；人物参考满足本次模型要求 | 只补影响当前视角或关键特征的图；人物资料在个人档案中一次补充并复用 | 保留搭配清单；可换单品或稍后预览，不能以虚构衣服冒充所选实物 |
| 判断长度 | 相应衣物长度、测量口径，以及该判断所需人体或真实试穿参考 | 例如只补裤长及相关人体参考，不自动索要全部围度 | 可继续看视觉方案，但不输出准确长度结论 |
| 判断局部松紧或合身 | 对应部位衣物尺寸、人体尺寸，以及需要的弹性、结构或有效试穿证据 | 只补当前部位信息，例如腰部尺寸或已有真实穿着反馈 | 标注该部位无法可靠判断，不阻止其他可支持的功能 |
| 按天气推荐 | 天气或手动环境条件；与保暖、防风等结论相关的衣物证据 | 优先使用已知结构及历史反馈；必要时轻问厚薄、内衬或实际体感 | 可给出一般搭配并说明不确定性，不把未知面料当成已确认防水或保暖 |
| 记录已穿过 | 单品或搭配引用 | 自愿点选合身、舒适与冷热感受 | 允许只记录“穿过”，不要求回答问卷 |
| 复用历史方案 | 当前单品仍可用，相关资料版本未失效 | 只检查变化部分 | 无变化直接复用，不重复索要资料 |

“被引用”必须区分浏览引用、候选引用和实际生成引用。只有本次输出依赖缺失证据时才出现补充请求，不因任何引用行为自动启动资料完善流程。

背面照仅在背面生成或结构判断需要时补；细节照仅在关键特征无法辨认时补。尺寸数据能约束评估，但不能保证生成模型会按尺寸准确绘制，仍需对照验证。

### 4.2 补充请求与频率

开发默认规则如下，后续可以根据使用测试调整频率，但不能取消证据边界：

1. 先复用档案、已导入商品资料和历史反馈，再检查能否后台提取，最后才向用户提问。
2. 同一次搭配请求最多主动展示一张补充卡，聚焦一件单品、一个动作，例如拍一张图或填写一项测量。不要按衣服数量连续弹窗。
3. 优先处理用户锁定单品中影响当前结果最大的缺口。非锁定单品优先提供可替换候选。
4. 如果一个动作不足以支持所需结论，卡片明确说明还需要其他资料。用户可主动进入分步补全，也可选择换单品、只看搭配清单或稍后处理；不能隐藏后续工作量。
5. 非关键补充放在详情页或结果页的可选入口，不拦截主流程。后台缺口记录不产生自动通知或强制待办。
6. 用户跳过后，同一请求不再追问；同一单品、字段与用途默认七天内不主动再次提示。用户主动补全、明确请求依赖该资料的判断或资料发生变化时可重新检查。
7. 冷却期内仍严格限制无法支持的结论，不能因为不再弹窗就默认资料足够。明确请求受限功能时，展示一次说明与替代路径。
8. 一次补充若解决多个缺口，统一更新，其他入口不重复收集。

补充卡内容固定包含：为什么需要、最小动作、替代资料入口、跳过的影响。例如：“要判断这条裤子的长度是否适合你，还缺裤长。可添加尺码表或按示意量裤长；暂不补充也可以继续看搭配，但本次不判断裤脚位置是否准确。”

不要使用“资料只完成 30%，请全部补齐”等施压文案。界面展示具体能力，例如“可用于搭配；长度判断缺少裤长”，而非无差别完整度。

### 4.3 结构化档案与文本描述并存

文字描述方便理解，稳定字段方便筛选。入库时保存简短描述、结构化属性和原图引用，避免每次重新读取全部衣橱图片。可提取品类、颜色、图案、领型、袖型、版型、搭配标签；尺寸、面料等必须标注来源。

完整档案可逐步包含名称、品牌、标注尺码、正背面与细节图、上衣衣长肩宽胸围袖长、下装腰围臀围裤长、面料成分弹性厚薄内衬、使用状态与穿着反馈。这是可完善范围，不是首次必填清单。

标注尺码不能代替实测尺寸，平铺宽度与围度不能混用。未知保留未知；AI 不得从照片猜出精确尺寸或面料成分作为事实，未经校准的置信分数也不是事实概率。

### 4.4 穿着中积累证据

用户主动记录穿过时可分散收集反馈，无需在入库时描述上身体感。反馈问题、展开条件与归因规则统一见[穿着反馈与搭配收藏](穿着反馈与搭配收藏.md)。反馈写回原单品的证据记录；涉及属性修正时遵守下述来源与确认规则。

### 4.5 避免完整资料单品垄断推荐

已确认：资料完整度只决定能支持哪些用途，不能直接等同于穿搭适合度。基础证据已满足的单品不应仅因缺少无关尺寸而被长期压低排序。

向搭配功能提供本次用途可用性与具体缺口，让普通搭配有机会使用轻量档案。涉及精确判断时仍保持证据门槛；不为增加曝光而放宽真实性要求。

## 5. 数据与状态

### 5.1 数据质量与保存

每条关键属性至少记录：字段名、值、单位或测量口径、来源类型、来源引用、确认状态、记录时间和适用的单品版本。未知值使用显式未知状态，不用 0 或空字符串冒充有效值。

来源类型至少区分用户实测、品牌尺码表、商品描述、用户观察或试穿反馈、AI 推断。确认“这张图是我的衣服”并不代表确认图中推断出的全部属性。

- AI 可以新增推断，不能静默覆盖用户确认值或实测值。
- 冲突值并存，注明来源；涉及本次判断时再请求确认，不在入库时集中追问所有冲突。
- 新导入的品牌尺寸不能覆盖改短后的实测尺寸；试穿反馈不能转换成未测量的数值。
- 衣服改短、缩水或结构变化时，标记受影响字段和预览为需复核；未受影响资料继续复用。
- 用户身体资料变化时，复核相关合身判断，不要求重新录入衣服基础资料。
- 模型升级只更新推断版本，不抹除旧证据；历史预览保留所用输入版本，不能伪装成依据新资料生成。
- 用户删除来源照片时，处理依赖该照片的可用性并遵循删除选择；不能仍把已不存在的图片作为可调用输入。

### 5.2 开发状态与处理边界

建议使用以下独立状态，避免将“保存成功”“识别成功”“可生成”合并为一个完成标记：

| 对象 | 建议状态或内容 |
| --- | --- |
| 单品档案 | 草稿、已入库、已归档；可穿或清洗中另设使用状态 |
| 图片与资料解析任务 | 待处理、处理中、成功、失败；失败可重试，不撤销已保存档案 |
| 用途检查结果 | 可执行、可执行但有明确限制、缺少必需证据；附缺失字段和可选路径 |
| 补充请求 | 单品、字段、用途、原因、优先级、跳过时间、下次可提示时间、解决状态 |
| 反馈 | 对应单品或套装、维度、部位、环境、时间、资料版本 |

用途检查逻辑：确认请求目标 → 收集当前证据 → 检查身份与来源冲突 → 确定能支持的输出 → 选择一个最高价值补充动作或替代路径 → 生成并记录输入版本。

解析、推荐与预览分别运行和保存结果。重试解析或重复提交不能重复创建同一单品；跨单品的相似图片只能提示疑似重复，不能直接合并。识别失败保留用户输入，解析完成也不能覆盖用户在等待期间手动修正的字段。

### 5.3 本地资料归属与生命周期

真实衣橱从首次录入起即保存在设备本地数据库及应用私有持久文件中，后续版本直接沿用。不建设云端衣橱、账号或同步流程；演示资料独立隔离。

选图后保存本地副本和稳定资源引用，不依赖临时相册 URI。原件与可清理缩略图缓存分开，文件写入失败不伪装入库成功。本地结构升级、敏感资料保护、系统云备份排除与删除规则见 [开发计划](../开发计划.md) 第 6.4 节。AI 使用用户手动配置的外部接口；资料提交 AI 按 APP 默认允许，限于当前任务所需，不整库上传。

## 6. 异常与替代路径

解析失败保留草稿和原输入，提供重试、截图或拍照入口。图像不足仍可保存，能否进入具体用途按第 4 节判断。

缺资料时不集中索要整套信息；按优先级给一个补充动作，或换单品、保留搭配清单、稍后再做相关判断。跳过不改变证据要求。来源冲突仅在影响当前用途时请求确认，不以 AI 猜测替用户解决事实冲突。

疑似重复只提示，不能自动合并不同实物；异步解析不能覆盖用户在等待期间手动修正的字段。原始资料删除后复核依赖，不把已删除文件继续作为可调用输入。

## 7. 功能依赖

[搭配生成](基于已有衣橱生成搭配.md)使用结构化资料筛选，再读取候选图片；[AI预览](AI上身预览.md)提出本次图片与证据需求；[天气适配](天气与场景适配.md)定义环境要求；[个人资料](个人资料管理.md)独立管理人体信息；[商品匹配](灵感搭配与商品匹配.md)将确认拥有的商品交给本功能入库；[反馈收藏](穿着反馈与搭配收藏.md)提供真实观察。

各调用方共用本功能的用途检查、补充请求和频率规则，不分别建立追问队列。

## 8. 验收条件与待确认事项

### 8.1 开发验收

1. 用户仅提供一张可辨认照片并确认单品与大类，即可入库；没有尺寸、品牌、面料和体感描述仍能保存。
2. 只有不可解析链接时能保存草稿，稍后补图不丢失已有资料。
3. 未确认具体尺码时，不把尺码表任意一行绑定为用户衣服尺寸。
4. 后台候选筛选与普通浏览引用不触发补全弹窗；同一次搭配请求最多出现一张主动补充卡。
5. 用户跳过补充后可保留方案、换单品或使用已有证据支持的功能；不会得到无依据的准确合身结论。
6. 补充一项资料后，其他入口能复用；重复请求和任务重试不会重复创建记录。
7. 已有足够商品图片时不强制补拍实物；缺少背面图不阻止仅依赖正面信息的用途。
8. AI 不能覆盖实测与已确认值；冲突、未知与数据来源可追溯。
9. 真实试穿反馈不会自动变成尺寸或面料事实；整套反馈不会无差别分配到所有单品。
10. 衣物或人体资料变化后仅复核关联判断，历史输入版本仍可识别。
11. 解析失败、用户跳过和生成失败分别处理，已保存档案与已选搭配不因此丢失。

同时观察首次入库完成率、主动操作数、入库耗时、每次搭配的补充次数、跳过率及实际试穿误差。减少录入操作的同时持续检查预览质量，不能仅以字段填写率或转化率评价方案。

新增验收：无需录完整衣橱即可完成一次任务；候选数量不设为首次使用硬门槛；缺类提示区分未录入和未拥有；用户跳过品类后明确输出范围；不因与当前用途无关的缺失字段排除单品。

首次体验观察从开始任务到用户首次确认满意方案的操作数和耗时，同时记录未完成任务的退出环节；后续实际穿着满意度另行验证，不能将确认方案当成试穿成功。

补充验收：本地资料经应用升级仍可用，升级失败不清库；断网可录入与编辑，原件不被缓存清理误删；AI 提交按默认允许执行并限于当前任务输入。

### 8.2 待验证事项

图片识别质量、商品解析能力、各品类最少证据、补充频率是否合理，以及用户实际录入负担。七天冷却与每次一张主动卡为当前开发默认，不是已经实测最优的参数。

### 8.3 分阶段使用示例

**旧裤子，没有商品链接：**

- 第一次：拍整体照，确认“下装”，保存。无需测量。
- 第二次：锁定它生成搭配，系统根据图片与已有衣橱提出组合，不因缺裤长而阻断普通搭配。
- 第三次：用户要求判断是否拖地，才检查裤长与相关人体参考；缺什么补什么，跳过则不输出准确长度结论。
- 第四次：实际穿着后点选“长度合适、腰部偏紧”，保存具体反馈，不生成虚假的腰围数值。

**新上衣，有商品资料：**

- 第一次：导入商品链接，确认款式与颜色；尺码已知则一起确认，不知道也可先保存。
- 第二次：匹配到正确尺码表后复用品牌尺寸，预览所需图片已有则不要求再拍。
- 第三次：洗后用户反馈缩水，只复核受影响尺寸及预览，不重做入库。

**衣服仅被系统列为候选：**

- 推荐系统在后台查看几十件衣服，不对这些衣服逐件发起补全。
- 最终套装中某件非锁定单品缺关键图时，优先换候选；用户坚持使用它再提供一次具体补充入口。
- 用户只浏览收藏或历史搭配时，不出现完善资料拦截。
