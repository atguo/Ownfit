# 灵感搭配与商品匹配

版本：v0.3｜后续阶段设计草案｜2026年10月26日  
所属项目：[项目计划书](../项目计划书.md)

## 1. 功能目标与问题

让用户从喜欢的元素或衣橱缺口出发，得到搭配方向，再找到具体商品，减少概念图很好看、买回实物却不一致的落差。

## 2. 范围与边界

支持已有单品、颜色、风格、参考图元素作为起点。该功能属于后续阶段，不是 MVP 前置条件。

范围包括概念方案、相似商品候选、替换后的评估与预览、购买后实物验证。商城接入、商品数据来源尚未确定；本规划不包含自动下单。

## 3. 使用场景与流程

锁定元素或接受衣橱缺口 → 生成搭配概念 → 查找候选商品 → 用户选定具体款式、颜色与尺码 → 替换概念单品 → 重新评估与预览 → 购买后验证实物 → 确认拥有后加入衣橱。

购买前验证使用商品真实资料；购买后验证使用实物与试穿反馈，两者不能合并为一次确认。

### 3.1 后期优先验证：我看中的这件能否配已有衣服

已确认，本模块后期实现。模块启动时优先验证用户提供具体待购商品的入口，再扩展 AI 概念生成与自动找相似款。

流程：用户提供商品链接或图片 → 确认具体款式、颜色及已知尺码 → 使用已录入衣橱生成可搭组合 → 检查资料与按需预览 → 用户自行决定是否购买 → 购买后实物验证与入库。

商品结果重点说明：可搭配哪些已录入单品、与已有单品的重复程度、是否形成新穿法或仅适合某一套，以及尺寸和面料缺失限制了哪些判断。重复不等于不值得买，作为参考，不替用户决定。

所有判断限定在“已录入衣橱”，不能把未录入衣服当作不存在，也不能据此宣称用户必须购买。资料不足时保留未知；不为了出结论虚构组合数量或准确度。

## 4. 关键设计与理由

概念衣服与真实商品采用明确标记，防止用户误以为生成款式一定可买到。商品匹配比较颜色、图案、版型、长度、面料与尺寸，不只比较图片相似度。

替换后必须重新检查：相似商品可能改变长度、厚薄与整体比例，原概念图不能继续充当商品上身结果。不能以概念生成的尺寸填补未知商品尺寸。

## 5. 数据与状态

概念方案保存锁定元素、搭配意图与单品描述。候选商品保存来源链接、获取时间、款式颜色尺码、图片、尺寸面料、匹配依据与缺失项；没有来源的字段保持未知。

区分概念、候选商品、已选择商品和用户确认拥有的实物。替换商品产生新的方案版本和相应预览输入版本，不改写原概念记录。

## 6. 异常与替代路径

找不到商品时保留概念，说明未匹配，不捏造商品或链接。链接失效、信息不足或无法获取资料时，允许用户自行提供链接、截图或选择其他候选。

只有相似款不能宣称完全一致；具体尺码未确认时不能作确定尺寸判断。购买后有色差、改版或尺码不符，按实物修正并复核相关预览。

## 7. 功能依赖

使用[搭配生成](基于已有衣橱生成搭配.md)的组合目标、[天气](天气与场景适配.md)的环境要求和[个人资料](个人资料管理.md)的偏好。[AI预览](AI上身预览.md)负责替换后的生成；[衣橱](衣橱资料入库与渐进完善.md)负责确认拥有后的入库；[反馈](穿着反馈与搭配收藏.md)负责实际验证记录。

## 8. 验收条件与待确认事项

新增验收：用户可从真实待购商品发起匹配；展示的组合对应已录入衣服；“重复”和“新增穿法”有具体单品或方案依据；未录入范围有明确说明；不要求先生成概念图才可使用该入口。开发排期保持后期，不加入 MVP 前置依赖。

验收：概念与商品可区分；候选具有真实来源；商品替换后旧预览不被展示为新商品结果；待购商品不会自动进入已有衣橱；资料不足不伪造；购买后能用实物补充与修正。

待验证：商城数据访问与使用条件、检索方式、匹配质量、商品信息可获得性和刷新策略。不得在接入验证前承诺覆盖特定商城。

## 本地资料与执行边界

本功能仍属后期。待购候选、比较结果及本地衣橱关联保存在设备上；联网搜索或商城跳转不等于获准上传人物照片或整套衣橱，具体查询数据范围实施前单独确认，不新增云端衣橱。
